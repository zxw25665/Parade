# 多节点实际测试方案（真实进程级 E2E）

> 本文档是设计文档，不是代码。目标：给出一个可立即落地的真实进程多节点测试 Harness 的精确设计，并明确标注哪些测试现在能做、哪些必须等生产 seam 变更落地后才能做。本文不修改任何生产代码、配置、现有测试或覆盖契约（`docs/coverage-contract.md`）。当前仓库**不存在** daemon 进程级多节点 E2E，`tests/test_cluster.ps1/.sh` 只是 Go 进程内与 libp2p wire 集成入口，这一点在覆盖契约第 52 行有明确说明。

## 1. 背景与目标

- 现状：后端正确性由三类测试支撑：`internal/core/sync` 的 3/5 节点进程内同步收敛、`internal/network` 的进程内 libp2p wire 测试、`internal/app` 的 stdio 单服务器管道测试与进程内用户流测试。它们都不跨真实 daemon 进程。
- 缺口：覆盖契约明确"daemon 进程级多节点 E2E 仍是后续覆盖工作"。真实进程才能验证：stdin EOF 退出路径、隔离数据目录、跨进程持久化（身份、队伍、对端列表）、重启补收、以及多节点聊天收敛。
- 目标：一套 Windows 优先（Unix 同构）的 Harness，按"现在可实现 / 阻塞"两档交付测试，阻塞项给出完整用例规格与自动启用门禁，不把 mDNS 或任何环境依赖现象计入判定。

### 2.2 stdio JSON-RPC 协议事实

- 传输：daemon 的 stdin/stdout，换行分隔 JSON-RPC 2.0（`stdio_server.go:12-24`）。每条响应或事件写后立即 flush。
- 请求参数必须是**数组**形式：反射注册表把 `params` 解析为 `[]json.RawMessage`（`jsonrpc.go:74-83`）。
- 响应回显请求 id；错误码：`-32700` 解析错误、`-32600` 空方法、`-32601` 未知方法、`-32603` handler panic、`-1` 应用错误（`stdio_server.go:123-151`）。
- 事件是**无 id 的通知**：`{"jsonrpc":"2.0","method":"event","params":{"event":"<名>","data":...}}`（`uds_ui.go:27-34`）。已知事件名：`ui_log`、`ui_peer_joined`、`ui_peer_left`、`ui_new_message`、`ui_peer_status`、`ui_file_progress`、`ui_file_completed`、`ui_conversation_updated`。
- 每行上限 1MB（`stdio_server.go:85`）。响应可能乱序（每行独立 goroutine dispatch），客户端必须按 id 匹配。
- `StdioServer.Start()` 把 Go 的 `log` 输出重定向到 stderr（`stdio_server.go:47-48`）。**在 Start 之前**，`daemon.go:92` 的 `fmt.Printf("warning: failed to load shared directories...")` 仍写 stdout，是当前唯一的预启动 stdout 污染点。
- stdin EOF 时读循环退出并关闭 `Exited()` 通道，daemon 在 `select` 中收到后走 `Shutdown()` 退出（`daemon.go:142-150`），退出码为 0。

### 2.3 网络与对端事实（含阻塞点）

- 默认端口 4327、默认监听 127.0.0.1（`config.go:61-73`）。`App.startNetwork` 里端口 0 回退 4327、监听地址空回退 0.0.0.0（`app.go:164-189`）。
- `--port 0` 是"未设置"而不是"随机端口"：`MergeWithCLI` 只在 `cli.Port != 0` 时覆盖（`config.go:227-229`），所以 `--port 0` 会被静默忽略并回落默认 4327。两个节点同机跑默认端口必然冲突。**端口必须显式分配，绝不用 0。**
- libp2p 监听 `/ip4/<listen>/tcp/<port>`；identify 明文 TCP 服务监听 `:port+1`（`libp2p_engine.go:159-185, 363`），每次连接返回一行 JSON `{"peer_id","uuid","pubkey"}`。
- `connectToPeer`（`libp2p_connect.go:24-144`）的端口推导是阻塞核心：
  - `identifyPort := e.port + 1`（**调用者自己的**端口），`discoverPeer` 拨 `ip:identifyPort`（`libp2p_connect.go:38-39, 146-178`）；
  - 随后拨 `/ip4/<ip>/tcp/<e.port>`，同样是**调用者自己的**端口（`libp2p_connect.go:51`）。
  - 即 `ConnectToPeer(ip)` 隐含假设"目标节点与调用者同端口"。目标端口不是对端真实端口。
  - 三阶段：phase1 连接、phase2 队伍挑战（`/parade/handshake/1.0.0`，回显加密 nonce）、phase3 测试消息（`/parade/test/1.0.0`，收 1 字节 ack）。成功后 `setPeer + savePeers + TopicPeerJoined`，App 侧自动触发 `StartPrivateConversation` 与 `syncAllConversationsWithPeer`（`app.go:239-257`）。
- 对端持久化 `.parade_peers`：`savedPeer{peer_id, uuid, pubkey, ip}`，`ip` 只在在线连接时从 live connection 提取（`libp2p_engine.go:639-671`）；`loadAndReconnect` 用 `ConnectToPeer(p.IP)` 重连（`libp2p_engine.go:694-733`），同样落入"按调用者端口推导目标端口"的坑。
- App 层 `SavePeer` / `ListSavedPeers` / `RemovePeer`：纯 IP 字符串，写 `<data-dir>/config.toml` 的 `[peers] saved`（`app.go:925-1001`），不携带端口。
- mDNS：服务名 `_parade._tcp`，启动失败非致命（`mdns.go:58-62`）；README"已知问题"承认环境依赖；`test_cluster.ps1` 设置 `SKIP_MDNS_TEST=1`。
- 网络在 `Login`（已有队伍时）或 `JoinTeam` 时才启动（`app.go:494-498, 565-570`）。启动前 p2p 端口与 identify 端口均未监听。
- 实例锁：非 `--debug` 时按 data-dir 上锁（`daemon.go:48-53`）；README 多实例示例使用 `--debug`。

### 2.4 现有测试覆盖（可复用基线）

- `internal/app/stdio_server_test.go`：os.Pipe 管道级单服务器测试，覆盖响应往返、广播、错误码、EOF 退出、在途排空、panic 隔离。进程内，不经真实 daemon。

- `internal/app/system_integration_test.go`：进程内完整用户流、`TestSystem_LoginAutoStartsNetwork`、`TestSystem_IsolatedDataDirs`。
- `tests/test_cluster.ps1`：仅 `go test` 三个包，明确不是进程级 E2E。

## 3. 范围划分（现在可实现 vs 阻塞）

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 单 daemon 真实进程 + stdio JSON-RPC 全套（spawn、多路复用、就绪、EOF 退出、重启持久化） | 现在可实现 | T0-T5；使用普通 IPC 模式，不使用 `--headless` |
| 跨端口连接门禁探测（T6） | 现在可实现 | 当前行为确定：失败或自连；同时作为 seam 落地探测器 |
| mDNS 诊断（T9） | 现在可实现 | 只记录，不进判定 |
| 同机多节点确定性互联 | **阻塞** | `ConnectToPeer` 按调用者端口推导目标端口（`libp2p_connect.go:38-39,51`）；对端持久化无端口；同机共享 127.0.0.1 时拨号必然指向调用者自己 |
| 双节点聊天收敛（T7） | **阻塞** | 依赖确定性互联 |
| 重启离线补收（T8） | **阻塞** | `loadAndReconnect` 复用同一错误假设（`libp2p_engine.go:722`） |

阻塞的唯一根因：**对端端点（含端口）没有进入连接路径**。第 5 节给出修复方向（seam 变更），第 6.3 节给出 T7/T8 完整规格与自动启用条件。

## 4. 进程 Harness 设计

### 4.1 节点模型与端口分配

- 节点 = 一个独立 `parade daemon` 进程 + 独立数据目录 + 独立 stdin/stdout/stderr 管道。规模先固定 2 节点（N 可扩）。
- 端口分配：`BASE = 44100`（远离默认 4327 与常见服务），节点 i 占用 p2p = `BASE + 2i`、identify = `BASE + 2i + 1`，端口对互不重叠。启动参数统一：`--debug --listen 127.0.0.1 --port <p2p> --data-dir <节点目录>`。`--debug` 与 README 多实例示例一致，跳过实例锁；回环监听避免防火墙干扰。**禁止 `--port 0`。**
- T0 预检：启动前对全部候选端口做 TCP 连接探活（`TcpClient` 短超时），占用即快速失败并给出占用人提示，不进入测试流程。
- 运行根：`$env:TEMP\parade-multinode\<run-id>`，run-id 每次运行唯一（时间戳 + 随机后缀），保证并发运行互不干扰；测试期间不清除他人目录。

### 4.2 隔离数据目录

- 每个节点目录独立包含：`.parade_data.db`、`.parade_identity`、`.parade_teams`、`.parade_peers`、`.parade.log`、`config.toml`。启动前该目录必须不存在或为空，由 Harness 创建。
- 每节点进程环境：`PARADE_DATA_DIR=<节点目录>`，并显式清空继承来的 `PARADE_PORT`、`PARADE_LISTEN`、`PARADE_DEBUG`、`PARADE_HEADLESS`、`PARADE_MDNS_ENABLED`、`PARADE_AUTO_RECONNECT`（`ApplyEnvOverrides` 会读这些变量，`config.go:142-173`）。
- 全局配置污染预检：Windows 的 `%APPDATA%\parade\config.toml`（Unix 的 XDG）**先于** data-dir 被加载（`config.go:75-97`），一份全局配置会同时作用到所有节点。预检发现该文件存在时输出警告并建议在隔离环境运行；不静默忽略。

### 4.3 进程启动与就绪判定

三层就绪，全部通过才算节点可用：

- R1 进程存活：spawn 后 1 秒内未退出，stdout 管道可读。
- R2 IPC 就绪：通过 stdio 发 `CheckHasIdentity` 并收到 id 匹配的响应（该方法无需登录，37 个既有方法之一，不新增方法）。轮询上限 10 秒。
- R3 网络就绪：在身份与队伍就绪后，TCP 拨 `127.0.0.1:<identify 端口>` 成功且读到一行含 `peer_id`/`uuid` 的 JSON（identify 服务在 `StartWithMDNS` 内启动，`libp2p_engine.go:363`）；同时以 `.parade.log` 中的 `libp2p engine started on port N` 与 `identify server on :N` 作旁证。轮询上限 30 秒。

身份序列（全用既有方法）：`CheckHasIdentity` 为 false 时先 `Register(<节点专属密码>)`，然后 `Login(<密码>)`，再 `JoinTeam(<共同 secret>)`（`JoinTeam` 内部触发 `startNetwork`）。这里不能使用 `--headless`，因为该模式不启动 IPC；普通 `--debug` 模式才提供 stdio JSON-RPC。用 `GetPubKey` 与 `GetActiveTeam` 校验身份与队伍状态。节点密码按节点区分，secret 全节点相同（保证队伍一致）。

### 4.4 stdio JSON-RPC 多路复用

- 每个节点一条读线程 + 一把写锁。读线程用 `bufio.Scanner`（缓冲区至少 1MB，与服务端上限对齐）逐行处理 stdout：
  - 有 `id` 且命中 pending 表 → 投递到对应等待者；
  - `method == "event"` 且无 id → 按 `params.event` 分发到事件订阅队列（`ui_new_message`、`ui_peer_joined`、`ui_peer_left`、`ui_conversation_updated` 等）；
  - 解析失败的行 → 记入 `<node>-stdout-contamination.txt` 证据文件，不崩溃（seam 未落地前容忍，落地后视为失败）。
- 每节点独立 id 空间（单调递增整数），pending 表 `id -> chan`；响应乱序由 id 匹配解决。写端互斥保证整行原子；请求 `params` 一律数组形式。
- 每请求超时默认 10 秒，超时即失败证据。事件断言用"订阅 + deadline 等待"，不用 sleep 轮询。
- 就绪、请求、事件三层各自独立，互不阻塞。

### 4.5 确定性连接阻断器（T6 门禁）

同机多节点、端口互异、共享 127.0.0.1 时，`ConnectToPeer("127.0.0.1")` 的行为是确定的坏行为：

- identify 拨号目标是 `127.0.0.1:<调用者 port+1>`（`libp2p_connect.go:38-39`），即调用者**自己的** identify 服务，读回自己的 `peer_id`/`uuid`；
- 随后 p2p dial 目标是 `127.0.0.1:<调用者 port>`，同样指向自己。

结果只有两种：phase1 失败，或"自连"（返回的 pubkey 等于本节点 pubkey）。**不可能确定性连到目标节点。** T6 把这一行为断言化：phase1 失败，或成功但 `pubkey == 本节点 pubkey`。当 T6 观察到"跨端口连到目标节点"（pubkey 等于目标节点 pubkey）时，判定 seam 已落地，自动启用 T7/T8。

### 4.6 mDNS 可选诊断

- 默认 `--mdns`（与产品默认一致），双节点就绪后等待 ≤30 秒观察 `ui_peer_joined` 或 `GetPeersWithStatus` 非空；另跑一轮 `--no-mdns` 验证关闭路径下无发现事件。
- 结果只写入报告（发现时间、对端信息），**不进入通过/失败标准**。mDNS 是环境依赖通道（README 已知问题；同机回环多播尤其不可靠），这是设计约束，不是缺陷。

### 4.7 清理（Windows 优先）

清理在 `try/finally` 语义下执行，任何路径都必须走到：

1. 对每个存活节点先关闭其 stdin 写端（EOF），等待退出 ≤10 秒，期望退出码 0（daemon 在 stdin EOF 时经 `Exited()` 优雅退出，`daemon.go:145-147`）。
2. 未在时限内退出 → Windows 用 `taskkill /PID <pid> /T /F`（`/T` 杀进程树，防子进程残留）；Unix 用 SIGTERM 再 SIGKILL。
3. 断言收尾：全部端口已释放（重新探活）、`Get-Process parade` 无残留。残留即失败证据。
4. 按 `--keep-artifacts` 决定是否删除运行根目录；默认删除，证据在删除前已归档（第 8 节）。

## 5. 所需生产 seam 变更（前置依赖，仅设计说明）

本方案**不实施**以下变更，只定义方向与验收探针。全部落点都在网络层与 daemon 组装层，RPC 方法表面（37 个）不变：

1. **identify 响应携带真实端点**：`{"peer_id","uuid","pubkey"}` 增加监听端口（或完整 multiaddr）。两处一致修改：`libp2p_engine.go:176-181`（明文 identify 服务）与 `libp2p_engine.go:303-310`（`/parade/identify/1.0.0` 流处理器）。
2. **对端持久化携带端口**：`savedPeer`（`libp2p_engine.go:639-644`）增加端口/端点字段；`savePeers` 写入、`loadAndReconnect`（`libp2p_engine.go:694-733`）读取并使用真实端点，而不是 `ConnectToPeer(p.IP)` 重新按调用者端口推导。
3. **连接入口接受 ip:port**：`ConnectToPeer` 内部（`libp2p_connect.go:24-144`）从"调用者端口推导"改为"显式端点优先，无端点再回退旧行为"；签名或解析层支持 `ip:port`，RPC 方法名与参数形状不变。
4. **stdio 纯净性**：`daemon.go:92` 的 `fmt.Printf` 改走 stderr 或 logBroker，保证 `ipcSrv.Start()` 之后 stdout 只含 JSON-RPC 行。

验收探针不依赖实现细节：T6 门禁反转（跨端口连到目标节点）+ T7/T8 全绿即视为 seam 达成。

## 6. 测试用例规格

### 6.1 现在可实现（T0-T5）

| 编号 | 名称 | 步骤 | 断言 |
| --- | --- | --- | --- |
| T0 | 预检 | 构建（复用 `pixi run build`）；端口空闲探活；无残留 parade 进程；全局配置污染检查；PARADE_* 环境变量隔离确认 | 全部通过才继续，任一失败快速退出并附证据 |
| T1 | 单 daemon stdio 生命周期 | spawn 节点 0（`--debug --data-dir <临时>`，不带 `--headless`），不发送任何请求；R1；`CheckHasIdentity` 往返；stdout 每行可解析为 JSON（seam 前降级为警告记录）；stdin EOF | 10 秒内退出码 0；响应 id 匹配 |
| T2 | 身份/队伍/网络启动流 | `Register` → `CheckHasIdentity=true` → `Login` → `JoinTeam(secret)` → `GetActiveTeam` 非空；R3 探活 identify 端口并读回本节点 JSON；检查 data-dir 生成全部 6 个文件，工作目录无新增 `.parade_*` | 全部通过；隔离成立 |
| T3 | stdio 多路复用与事件 | 登录后并发发 3 个请求（`CheckHasIdentity`、`GetPubKey`、`GetActiveTeam`）；`SendTeamChat("ping-<ts>")` | 响应按 id 一一匹配（允许乱序）；≤10 秒收到本节点 `ui_new_message`；`GetConversationMessages` 包含该消息 |
| T4 | 单节点重启持久化 | T3 后 EOF 退出；同 data-dir、同端口重启；`Login`；`SavePeer("10.0.0.5")` → `ListSavedPeers` → `RemovePeer` | 重启后 `GetConversationMessages` 仍有原消息；saved peers 列表与 `<data-dir>/config.toml` 的 `[peers] saved` 一致 |
| T5 | 单节点事件完整性 | 连续 `SendTeamChat` 两次 | 恰好两条 `ui_new_message`，按内容匹配，无重复无丢失 |

### 6.2 门禁与诊断（T6、T9）

| 编号 | 名称 | 步骤 | 断言 |
| --- | --- | --- | --- |
| T6 | 跨端口连接门禁 | 节点 0（port A）与节点 1（port B，A≠B）各自完成身份与入队；节点 0 调 `ConnectToPeer("127.0.0.1")` | seam 前：phase1 失败，或成功但返回 `pubkey == 节点 0 自身 pubkey`（自连）；seam 后：pubkey == 节点 1 pubkey（自动启用 T7/T8） |
| T9 | mDNS 诊断 | 双节点默认 `--mdns` 等 ≤30 秒；再跑一轮 `--no-mdns` | 发现结果（时间、peer 信息）记入报告；任何结果不影响判定 |

### 6.3 阻塞用例（T7、T8，完整规格，seam 落地自动启用）

| 编号 | 名称 | 步骤 | 断言（≤60 秒 deadline） |
| --- | --- | --- | --- |
| T7 | 双节点聊天收敛 | 两节点入队同一 secret 并互联；节点 0 连发 5 条 `SendTeamChat`；节点 1 收齐后回 2 条 | 节点 1 收到全部 5 条 `ui_new_message`（按 HLC/内容匹配，顺序有序）；`GetConversationMessages` 双向一致（数量、内容、HLC 集合相等）；至少一次 `ui_conversation_updated`（merkle 同步完成信号）；节点 0 收到节点 1 的 2 条 |

## 8. 失败证据与工件

运行根目录（第 4.1 节）下归档：

- `<node>-stdout.log`、`<node>-stderr.log`：每节点完整管道输出；
- `<node>/data/.parade.log` 拷贝：daemon 日志（引擎日志只进此文件，不经 stderr）；
- `<node>-stdout-contamination.txt`：stdout 非 JSON 行记录（T1 与 seam 纯净性依据）；
- `run-summary.json`：每用例结果、耗时、断言详情、节点退出码；
- 失败时若 IPC 仍存活：先对每个节点 dump `GetPeersWithStatus`、`GetConversationMessages`、`ListSavedPeers`、`GetActiveTeam` 到 `evidence-state-<node>.json`，再走清理；
- 任一 daemon 退出码非 0 或超时被 kill → 对应用例失败；报告末尾打印工件目录绝对路径。

## 9. 通过 / 失败标准

套件通过（全绿）：

1. T0-T5 全部通过；
2. T6 按当前断言通过（seam 前：失败或自连；seam 后：反转断言）；
3. T9 完成记录；
4. 阻塞用例 T7/T8：seam 未落地时以 SKIP 列出并引用第 5 节依赖；落地后必须全绿；
5. 清理后无残留进程、无占用端口；
6. 所有失败都有对应工件（第 8 节）。

明确**不计入**判定：mDNS 发现结果；`ConnectToPeer` 返回的 phase2/phase3 细节（仅诊断字段）；任何缺证据的观察。

## 10. Windows 与 Pixi 入口

- 编排入口：`tests/multinode/run.ps1`（Windows 原生 PowerShell，与 `test_cluster.ps1` 的 win-64 模式一致；Unix 侧同构 bash）。
- stdio 客户端：`tests/multinode/rpc_stdio.py`，仅用标准库（subprocess / threading / json），python>=3.12 在 pixi 依赖内，零第三方依赖。多路复用、事件订阅、超时、证据归档都在这一层。
- pixi 注册（沿用现有 `[target.win-64.tasks]` 覆盖模式，`pixi.toml:66-70`）：

```toml
test-multinode = { cmd = "powershell -NoProfile -ExecutionPolicy Bypass -File tests\\multinode\\run.ps1", depends-on = ["build"] }
```

- 二进制路径沿用 `test_backend_fixes.sh` 的 `PARADE_BIN` 环境变量覆盖约定（Windows 上为 `parade.exe`）。
- Windows 清理铁律：stdin EOF 优先（关闭写端 → 期望退出码 0）→ 10 秒未退出 → `taskkill /PID <pid> /T /F` → 端口与进程残留复核。

## 11. 风险与限制

- 端口段被占用：T0 快速失败并提示占用人，不误报测试失败。
- libp2p 对自拨号（dial 自己）的行为随版本可能有差异，T6 断言以"pubkey 不等于目标节点 pubkey"为准，不只依赖 phase1 结果。
- Windows 下关闭父进程的 stdin 写端不一定即时触发子进程 EOF（管道语义），清理必须带 10 秒超时后强制 taskkill。
- `ui_peer_joined` 事件带 5 秒去重（`app.go:243-248`），T5/T7 的断言以消息内容与 HLC 为准，不依赖该事件计数。
- 全局用户配置（`%APPDATA%\parade\config.toml` 等）会先于 data-dir 加载并作用于所有节点，预检告警，建议隔离环境运行。
- mDNS 结果不作为任何判定依据，这是约束不是缺陷。
